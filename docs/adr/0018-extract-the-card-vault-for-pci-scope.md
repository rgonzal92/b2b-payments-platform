# Extract the Card Vault for PCI scope

The Card Vault leaves the platform as `vault-service`, a Maven module in this repo with its own PostgreSQL, a gRPC API for the platform and one HTTP route for revealing Card Details. The force (ADR-0003) is PCI scope reduction: while the vault is a module, its table shares the platform's database, its keys share the platform's environment, and `suppliers` and `clearing` handle decrypted PANs, so every line of the platform is in scope. After M7 the platform holds no PAN at rest or in memory (ADR-0004 as amended).

Three changes come together, because extraction alone would move the PANs but not shrink what can reach them. Envelope encryption gives each card its own data key, wrapped by a key-encryption key that lives only in OpenBao Transit, so reading `vault-service`'s database and environment reveals nothing without OpenBao. Mutual TLS covers every hop that carries a PAN or the vault's keys: platform and Gateway to `vault-service`, the Network to `authorization-service`, and `vault-service` to OpenBao and to its database. And the two paths that brought PANs into the platform are rerouted: a Supplier's Remittance Advice link answers with a 60-second Ed25519-signed grant that redirects to `vault-service` through the Gateway, and `vault-service` takes the Network's Clearing File and hands the platform a copy with Card Tokens in place of PANs.

Issuance can no longer be one transaction. The Payment saga records a fresh Card Token first, `vault-service`'s `IssueCard` is idempotent by it, and `cards.card` commits after; a Payment that stops in between leaves an orphan card secret, which we accept rather than build a reaper. While the Card Vault is unavailable, the issue step waits and retries without counting attempts, so an outage holds Payments rather than failing them, and an alert fires after 5 minutes. A Remittance Advice link is no longer used up on opening; `vault-service`'s `revealed_at` is the one "once", so a reveal that fails leaves the link working.

Scope moves rather than vanishes. `vault-service` and OpenBao are in scope; the Gateway is, as transit-only; and `authorization-service` is, because it hashes the Network's PAN in memory with the shared `CARD_HASH_KEY`. We rejected hashing through OpenBao, since a Transit call per Charge doesn't fit ADR-0010's p99. We rejected keeping the reveal in `suppliers` and letting `clearing` call the vault per record, since either keeps PANs passing through the platform. We rejected keeping one static encryption key in the environment, since whoever reads it reads every card. The costs are a new app to run and keep up (a Card Vault outage holds up issuance, reveals and Clearing imports, though not Authorization), OpenBao to initialise and unseal (dev mode in Compose, one file-backed pod with its unseal key in a Secret in the cluster, neither production-grade, with its key-encryption key rotated by hand), and certificates that expire every 24 hours in the cluster.
