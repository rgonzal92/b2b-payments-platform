# Reactor and WebFlux

## The problem it solves here

`authorization-service` answers every Charge in real time, and the M5 design makes its hot path reactive (ADR-0016, "The service's hot path"): no thread waits while PostgreSQL commits. In the platform each Authorization holds a thread from the gRPC request to the commit; in the service a call holds a thread only while there is work to do, and between the statements it's just a pipeline waiting for R2DBC's next result. WebFlux serves only the service's HTTP (actuator, health); the hot path is gRPC, and since Spring gRPC documents nothing reactive, the bridge from its handler to Reactor is ours (#89). The design expects no p99 gain, because M4's misses came from the disk's commit flushes, which no thread model removes; #97 measures it.

## Mental model

- **A `Mono` is a recipe for at most one value, not the value.** `authorizations.authorize(charge, now)` returns at once with a `Mono<Authorization>` that has done nothing yet. Each operator adds a step: `map` transforms the value, `flatMap` starts the next asynchronous step (the next SQL statement) with it, `switchIfEmpty` says what to do when there is none (no card has the PAN), `then` waits for completion and drops the value.
- **Nothing runs until someone subscribes.** WebFlux subscribes to a controller's `Mono`; for gRPC, `IssuerAuthorizationService` calls `subscribe(onValue, onError)` itself and returns. The call's thread is then free; the value arrives later, on whichever thread completes the last step.
- **Steps run on the thread that delivered the previous result.** R2DBC's driver reads PostgreSQL's replies on reactor-netty's event loop threads, so everything after the first query (hashing the security code, the rules, building the answer, `responseObserver.onNext`) runs there. That makes the rule simple: nothing in the pipeline may block. CPU work such as an HMAC is fine; `block()`, JDBC, `Thread.sleep` or a synchronous HTTP call are not, and Reactor throws if `block()` is called on one of its non-blocking threads.
- **The gRPC side has its own threads.** grpc-java runs each call's interceptors and handler on an executor, separate from Netty's I/O event loop. Its default is an unbounded cached pool, so a handler that waited for the database would simply get a new thread per waiting call and pass every test. The service sets a fixed pool of four `grpc-call-` threads (`GrpcCallThreads`), and `NetworkLinkTests` holds more Charges on a locked table than there are threads while a Reversal still gets its answer. Replacing `subscribe` with `block()` makes that test fail.
- **The token check stays off Netty's event loop.** Spring gRPC's `AuthenticationProcessInterceptor` is blocking: the JWT decoder fetches Keycloak's key set on the first call and again when it refreshes. On the call threads that costs one call a few milliseconds now and then; on the event loop it would stall every connection it serves.
- **Transactions follow the subscription, not the thread.** `@Transactional` on a method returning `Mono` wraps the returned `Mono`: subscribing begins the transaction, its completion commits, an error rolls back. The connection travels in the subscription's Reactor context, so every `DatabaseClient` statement in the pipeline joins it, whatever thread it runs on. `ThreadLocal`s (the MDC, Spring Security's context) don't follow; Micrometer's context propagation does that, and #96 brings the trace across.
- **Errors and cancellations are signals too.** An exception anywhere in the pipeline skips the remaining steps and reaches `onError`, which answers the Network `UNKNOWN`, as a thrown exception would in a blocking handler; since #93 an Authorization's errors are turned into a `91` answer first ([`resilience4j.md`](resilience4j.md)), so only a Reversal's reach `onError`. When the Network gives up (its 1-second deadline), gRPC cancels the call, but the pipeline isn't disposed: the Authorization commits, so a resend or Reversal finds it, as in the platform. The one cancel that does reach the pipeline is the Authorization's own 500 ms time limit, and it rolls the transaction back.

## Gotchas we hit

- **A method returning `Mono` still runs its body at once.** Under `@Transactional` the body runs before the transaction begins; only the statements in the returned `Mono` are inside it. `Authorizations.authorize` wraps its first step in `Mono.defer`, so even hashing the PAN waits for the subscription.
- **`defaultIfEmpty(value)` builds its value eagerly.** `defaultIfEmpty(new Decision(null, decide(…)))` ran the rules for an unknown card on every call, even when a card was found. `switchIfEmpty(Mono.fromSupplier(…))` builds it only when the query comes back empty.
- **Answering a cancelled call throws.** grpc-java's `ServerCallStreamObserver.onNext` throws once the call is cancelled, unless the handler set a cancel handler. The bridge sets one and checks `isCancelled()` before answering, so a late answer is dropped instead of failing the subscriber.
- **Spring Boot makes no `JwtDecoder` in a WebFlux app.** Its reactive auto-configuration builds a `ReactiveJwtDecoder` for HTTP, but Spring gRPC's security wants the blocking `JwtDecoder`, so `SecurityConfig` declares one, resolved from the issuer at the first call so the service starts while Keycloak is down. The test's stand-in decoder is `@Primary` beside it; giving both beans one name fails the context, since bean overriding is off.
- **Adding Spring Security would close every HTTP path.** With a reactive JWT decoder present, Spring Boot's default chain wants a token for all of WebFlux, `/actuator/health` included. `SecurityConfig` declares the chain itself and leaves health open, as the platform does.
