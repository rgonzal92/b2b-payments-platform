# OpenBao

## The problem it solves here

Until M7 the Card Vault encrypts every PAN under one AES key, `VAULT_ENCRYPTION_KEY`, read from the platform's environment. Whoever can read that environment, or a heap dump of the process, can decrypt every card ever issued, and rotating the key means re-encrypting every row with the old and new key side by side. M7 moves the Card Vault into `vault-service` and takes the key out of every app's environment (design Q3, Q10): the key that protects the cards, the key-encryption key, lives only in OpenBao, an open-source fork of HashiCorp Vault under the Linux Foundation, and no app ever holds it. `vault-service` holds only an OpenBao token whose policy lets it ask for data keys and unwrap them, one card at a time.

## Mental model

- **Envelope encryption: two layers of keys.** Each card gets a fresh data key (DEK), and the PAN and security code are encrypted under it with AES-256-GCM, the Card Token as associated data, exactly as the platform's vault encrypted under its one key. The data key itself is then encrypted ("wrapped") under the key-encryption key (KEK) and stored beside the ciphertext. Reading a card means unwrapping its data key first; stealing the database gives ciphertext and wrapped keys, both useless without the KEK. Losing one data key in memory exposes one card, not all of them.
- **Transit is encryption as a service.** OpenBao's Transit secrets engine holds named keys (here `card-kek`) and performs operations with them on request; the key material never leaves OpenBao. `vault-service` uses two endpoints: `POST /v1/transit/datakey/plaintext/card-kek` returns a new random data key twice, in clear (to encrypt with, then forget) and wrapped (to store); `POST /v1/transit/decrypt/card-kek` turns a wrapped key back into the clear one. Transit never sees a PAN: only data keys cross the wire.
- **The ciphertext names the key version.** A wrapped key looks like `vault:v1:/5vJtd7h...`: the `vault:` prefix (kept from HashiCorp Vault for compatibility), the KEK version that wrapped it, then base64. Rotating the KEK (`transit/keys/card-kek/rotate`) adds version 2 for new data keys while version 1 still decrypts the old ones; `transit/rewrap` re-wraps a stored data key under the newest version inside OpenBao, without the caller seeing it in clear. That is how #139's rotation job will move every card without decrypting a PAN.
- **Policies are deny-by-default path rules.** An OpenBao token can call only the paths its policies grant. `vault-service`'s policy (`openbao/dev-init.hcl`) grants `update` on exactly three paths, `transit/datakey/plaintext/card-kek`, `transit/decrypt/card-kek` and `transit/rewrap/card-kek`, so a stolen service token can't rotate, read, export or delete the key, nor use Transit to encrypt or decrypt anything else. Its token is created without the `default` policy, so it can't even look itself up.
- **Seal and unseal.** A real OpenBao server starts sealed: its storage is encrypted, and it must be given its unseal key (or an auto-unseal KMS) before it serves anything. A sealed or restarting OpenBao answers `503`, which `vault-service` reports to its caller as gRPC `UNAVAILABLE`, so the Payment waits rather than fails (design Q23).
- **Dev mode skips all of that.** `bao server -dev`, the image's default command, runs in memory, already initialised and unsealed, with a root token of your choosing (`BAO_DEV_ROOT_TOKEN_ID`). That's what Compose and the tests run. The cluster's OpenBao, with file storage, an unseal step and Kubernetes auth, is #140's.

## How it's set up here

- **Compose** runs `openbao/openbao:2.7.1` with the dev root token `OPENBAO_DEV_ROOT_TOKEN` from `.env` and mounts `openbao/` as its config folder. On start OpenBao runs `openbao/dev-init.hcl`, its declarative self-initialization: `initialize` blocks of API requests it makes on itself. They mount Transit, create `card-kek`, write the `vault-service` policy, raise the token engine's maximum lifetime and create `vault-service`'s token with `OPENBAO_TOKEN` (from `.env`) as its ID. So the app's token is fixed per `.env` even though dev mode forgets everything on restart: each restart recreates it.
- **`vault-service`** calls Transit with Spring's `RestClient` and the `X-Vault-Token` header (`openbao.Transit`): two JSON calls didn't justify a client library such as Spring Vault.
- **Tests** run the same image in Testcontainers with the same `dev-init.hcl`, so the policy the tests run under is the one Compose uses, and `IssueCardTests` unwraps a stored data key with the root token to prove the row decrypts back.

## Gotchas we hit

- **Dev mode loses the KEK on restart, and with it every card.** The cards in `vault-postgres` survive a restart of the `openbao` container, but the `card-kek` that wrapped their data keys doesn't: a new one is created, and every card issued before can no longer be decrypted. Reset `vault-postgres` with it in development. Real deployments keep OpenBao's storage, which is why the cluster's has file storage.
- **Self-initialization revokes its own root token, and every child of it.** The `initialize` requests run under a temporary root token that OpenBao revokes when they finish. A token created there is that token's child and dies with it, so the service's token is created with `no_parent = true` (an orphan).
- **Tokens expire after 32 days by default.** The token engine's default maximum lifetime is 768 hours; a dev stack left running longer would lose its service token. `dev-init.hcl` raises the engine's maximum and gives the token 10 years.
- **Self-initialization reads secrets from the environment, not from the file.** The token ID comes in through `eval_source = "env"`, so `dev-init.hcl` holds no secret and can be committed.
- **A read-only config mount trips the entrypoint's `chown`.** The image's entrypoint tries to `chown` `/openbao/config`; on a `:ro` mount that prints an error. `SKIP_CHOWN=true` turns it off.
- **`datakey/wrapped` is not enough to encrypt.** It returns only the wrapped key, for encrypting later elsewhere; issuing needs `datakey/plaintext`, which returns both, so that's the path the policy grants.
- **The clear data key lives briefly in memory, and not only in our byte array.** `Cards` overwrites the data key's bytes once the PAN and security code are encrypted, but the JSON response's base64 string stays on the heap until it's garbage-collected, and so does the copy of the key bytes each `SecretKeySpec` in `CardCrypto` takes, which nothing wipes. Java can't wipe a `String`; the exposure is one card's key, for a moment, in `vault-service`'s own process.
