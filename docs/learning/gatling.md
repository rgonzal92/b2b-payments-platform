# Gatling

## The problem it solves here

ADR-0010 promises that the Issuer answers 99% of the Network's Authorizations within 100 ms; since the cutover (#92) `authorization-service` answers them, not the platform. A promise about a p99 needs load to check it: thousands of Charges at a steady rate, the latency of each recorded, and a report that says whether anything failed. Gatling generates that load from a simulation written in Java (`load-test/src/test/java/.../AuthorizeSimulation.java`), calls `Authorize` over gRPC on `localhost:9090` as the Network (the platform until #92, `authorization-service` since; in the k3d cluster `dns:///authorization-service:9090` with `round_robin`, from the `target` and `loadBalancingPolicy` properties, #116), and writes an HTML report of every call's response time.

Since #117 a second simulation, `InvoiceSimulation`, has Acme's ERP submit Invoices over HTTP through the Gateway at 5 a second, so a redeploy of the platform and the Gateway is checked the same way; `scripts/k8s-load-test.sh` runs both side by side in the cluster.

## Mental model

- **Open vs closed workload.** A *closed* model keeps a fixed number of users busy: a new Charge starts only when one finishes, so a slow platform quietly lowers the rate and hides its own slowness. An *open* model starts users at a fixed arrival rate whatever the platform does, as a card Network does: Charges keep arriving while earlier ones are still waiting. We wanted an open model. Gatling's open-source gRPC support allows only 5 virtual users per run (below), so the simulation is the next best thing: a *paced* closed model. 5 users each start a Charge every 25 ms (`pace`), 200 a second together, as long as every answer comes within 25 ms. A slower answer delays only its own user's next Charge, so slowness shows as a lower achieved rate as well as latency: compare the report's requests per second with 200.
- **The Java DSL.** A simulation is a class extending `Simulation` whose constructor calls `setUp(...)`: *scenarios* (what one user does: a chain of `exec`, `randomSwitch`, `doIfOrElse`, `group`) each get an *injection profile* (how users arrive), plus *protocols* (where to send calls) and *assertions* (what makes the run fail). Here each of the 5 users loops (`during`) through Charges, one per pace.
- **gRPC.** `gatling-grpc-java` sends calls through the stubs generated from the `contracts` module's `.proto` file: `grpc("name").unary(IssuerAuthorizationGrpc.getAuthorizeMethod()).send(...)`. *Checks* decide whether a call passed: the gRPC status is `OK` and the response code is the one this kind of Charge expects (`00`, `57`, `N7`). A call whose check fails is a failed call, and the assertion `global().failedRequests().count().is(0L)` turns any into a failed build.
- **Client-side vs server-side time.** Gatling times from sending the request to reading the answer, including the network and its own scheduling. The server's Micrometer timer (`grpc.server`, on Grafana's Authorization dashboard; the platform's until #92, `authorization-service`'s since, exported to Grafana since #96) times only the server's work. The 100 ms target is the server-side p99; Gatling's numbers sit beside it and should be a little higher.

## Reading the report

The console prints a summary at the end, and `load-test/target/gatling/<run>/index.html` holds the full report. Each row is a request name (`Measured: approved charge`, `Measured: second charge`, `Measured: wrong security code`, and the same under `Warm-up`), with counts of OK and KO (failed) calls, requests per second and response-time percentiles: the defaults are p50, p75, p95 and p99. Read the three **Measured** rows for the result: the warm-up includes the JVM compiling the hot path, which is why it is reported apart. The group rows (`Warm-up`, `Measured`) show zeros for their times in this simulation; read the request rows. The *Response Time Percentiles over Time* chart shows whether latency drifted during the run (a queue building up) or stayed flat.

## Gotchas we hit

- **Gatling's `csv()` works only inside a running simulation.** Called from a unit test, it throws "Simulations can't be instantiated directly". The cards file has no quoting, so `CardsFile.read` parses it with plain Java, and its unit test runs in CI.
- **Cards come from a queue, not a Gatling feeder.** The approval chain appears in three branches and both phases, and a card handed out twice gets a `57` on its second Charge, a failed call. One shared queue of fresh cards, and one of cards the run has charged for the declines, guarantees each fresh card is charged once.
- **A channel per user is Gatling's default.** At 200 users a second that measures HTTP/2 connection set-up, not Authorizations. `shareChannel()` sends every call over one channel, as the Network keeps one connection to the Issuer.
- **Spring Boot's dependency management downgrades Gatling.** The module inherits Spring Boot's parent, which pins Netty, grpc-java and protobuf to Spring Boot's versions. The module's pom sets them back to the versions Gatling 3.16.0 was built against; update them with Gatling.
- **The load test must not run in CI.** The Gatling plugin's run is bound only in the `load-test` profile, so `./mvnw verify` compiles the simulation and runs its unit tests, and a measured run is always by hand: `-Pload-test`.
- **The open-source gRPC plugin is a trial.** `gatling-grpc` logs "GATLING GRPC TRIAL VERSION" and calls `System.exit` when a run starts its sixth virtual user, or after 5 minutes. An open model at 200 a second starts 200 users a second, so it died at once; hence the 5 paced users. Lifting the limit takes Gatling Enterprise.
- **The 5-minute cap is a hard stop, timed from the first user.** `io.gatling.grpc.enterprise.Usage$` calls `System.exit(1)` 300 s after the first virtual user starts, whatever the simulation is doing: no report, and Maven fails. A run's warm-up plus measured window must end well inside that (the simulation also refuses more than 240 s, the life of its Network token), so a longer run, such as #119's local 200-a-second run through the rollouts, can't simply be lengthened. It is also what ends a run in which a call never gets an answer: the stuck user keeps Gatling from finishing until the cap exits with an error, which is how `scripts/k8s-load-test.sh` fails on a missing answer (#116).
- **A ramp shorter than a second injects no one.** `rampUsers(5).during(250 ms)` ran a simulation that ended at 0 s with all 5 users still waiting; the users now ramp in over 1 second.
- **Fresh cards run out.** A Single-Use Card takes one approved Charge, so each run needs about 27,300 fresh cards: seed 25,000, then 3,000 more with `append=true`. The simulation counts them before it starts and stops at once if the file runs dry mid-run.
- **Gatling's HTTP support has no user cap.** The 5-user and 5-minute trial limits belong to `gatling-grpc` alone, and each simulation runs in a JVM of its own, so `InvoiceSimulation` uses a true open workload (`constantUsersPerSec`), with `shareConnections()` so its users share one keep-alive pool, as an ERP's HTTP client does. Without it each new user opens its own connection, and a redeploy would never meet a request on a kept-alive connection to a stopping pod, the case worth testing.
- **Gatling resends a request when its pooled connection closes first.** If a connection taken from the pool closes before the answer arrives, Gatling's HTTP client sends the request once more on a new connection, whatever its method (`DefaultHttpClient.canRetry`: any request from a pooled connection, unless its body is a stream already read). The report counts it as one OK request. Through a Gateway pod's shutdown that is what keeps a lost connection from failing the run, and it is safe only because the resend carries the same `Idempotency-Key`, which the platform answers with the original `201`: a client without the key would submit the Invoice twice.
- **Two simulations at once can't each run Maven in one checkout.** Each build regenerates and recompiles `contracts` and the simulations into the same `target/` while the other's simulation is loading classes from it. The cluster's Job (`scripts/k8s-load-test-job.sh`) builds once with `install -Pload-test -Dgatling.skip=true`, which also fetches Gatling's plugin, then runs `gatling:test` for each simulation offline (`-o`, `-Dgatling.simulationClass=…`), side by side, prefixing their lines with `[authorize]` and `[invoices]`.
- **Three rollouts don't fit in 60 seconds.** The first run through the service, the platform and the Gateway ended its simulations while the Gateway's last old pod was still stopping, about 65 s in on a workstation; CI's runner is slower. `DURATION` is 180 s since #117, which still leaves gatling-grpc's 5-minute cap and the 240 s token limit a margin.
