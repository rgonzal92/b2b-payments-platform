# Kubernetes

## The problem it solves here

Every app runs as one process started by hand, so replacing it is an outage (M6 design, Problem). Kubernetes runs each app as a set of replaceable copies behind a stable address and replaces them one at a time; M6 uses it for that operability, not for scale (ADR-0017). #114 puts the whole stack on one single-node cluster; #116 runs `authorization-service` as two pods that the Network's Charges survive a rolling restart of. The cluster is k3d: k3s, a small Kubernetes distribution, running as a Docker container, so a laptop with Docker is enough.

## Mental model

- **You declare objects; controllers make them true.** `kubectl apply` stores the desired state in the API server, and controllers keep comparing it with what runs and correcting the difference. Nothing is started by a command: a deleted pod comes back because its Deployment still asks for one.
- **A pod is the unit that runs:** one or more containers sharing a network address and volumes. Pods are disposable; nothing addresses one by name for long.
- **A Deployment keeps N identical pods of a stateless app** and replaces them when the template changes. The four apps are Deployments (`deploy/helm/b2b-payments/templates/_app.tpl`).
- **A StatefulSet is for pods with an identity and their own disk:** pod `postgres-0` always gets the volume claim `data-postgres-0`, provisioned here by k3s's local-path storage, so a restarted database finds its data. PostgreSQL ×2, Kafka, Keycloak and otel-lgtm are StatefulSets, one replica each, with the images `compose.yaml` pins (the infra subchart). Keycloak and otel-lgtm keep no volume: Keycloak imports the realm again into each fresh pod.
- **A Service is a stable name and address in front of pods selected by label.** Inside the cluster `http://keycloak:8180` or `kafka:9092` resolves through the cluster's DNS to the Service, which forwards to a ready pod. `ClusterIP` (the default) is reachable only inside the cluster; `LoadBalancer` also gets an external address, which k3s's built-in ServiceLB provides on the node, and k3d maps the node's ports to `127.0.0.1` on the host. The Gateway (`8080`), the simulator's demo (`8081`) and Keycloak (`8180`) are LoadBalancers; Grafana is reached with `kubectl port-forward service/lgtm 3000`.
- **Probes: three questions the kubelet keeps asking each container.** Each reads one of Spring Boot's actuator probe groups, which Boot turns on by itself when it finds itself on Kubernetes (`_app.tpl`).
  - *Readiness*, `/actuator/health/readiness`: should the Service send this pod traffic? Until it answers `200` the pod is left out of its Services' addresses; it never restarts anything. Boot's readiness group holds only its own readiness state, not the database: when the database goes, every pod shares the outage, and dropping them all from the Service would turn fast `91`s into connection errors (M6 design, Two copies of each app). We checked it: with `authorization-postgres` scaled to 0, both service pods stayed `1/1`. A pod that is running but not ready is the commonest failure ([`pod-not-ready.md`](../runbooks/pod-not-ready.md)).
  - *Liveness*, `/actuator/health/liveness`: is the process wedged beyond repair? Three failures in a row and the kubelet restarts the container. Boot's liveness group is the process alone; putting a dependency in it would restart every pod whenever that dependency failed, which fixes nothing.
  - *Startup*, on the liveness path too: holds liveness off until the app first answers, here for up to 3 minutes, so a slow start on a busy machine isn't mistaken for a hang.
- **A rolling update replaces pods one at a time.** A Deployment's template change (a new image, or the timestamp `kubectl rollout restart` adds) creates a new ReplicaSet and moves pods to it: by default it may run one pod over the replica count and none under it, so with 2 replicas it starts a new pod, waits until it is ready, stops an old one, and repeats. Readiness is what makes that safe; `kubectl rollout status` waits for the end.
- **Stopping a pod races two things.** Kubernetes removes the pod from its Services' addresses and, at the same moment, runs its `preStop` hook and then sends `SIGTERM`. Clients that haven't heard of the removal yet still send requests, so each app sleeps 5 s in `preStop` (Kubernetes' own `sleep` action: the buildpack image has no shell) before Spring Boot's graceful shutdown stops accepting work and finishes what is in flight. `terminationGracePeriodSeconds` (40) bounds the whole stop, after which the container is killed. Boot's shutdown runs its lifecycle phases one after another, and two of them wait for work in flight: the service's gRPC server stops first, synchronously, for up to `spring.grpc.server.shutdown.grace-period`, which Boot's per-phase timeout doesn't bound, and then the web server's graceful phase waits up to `spring.lifecycle.timeout-per-shutdown-phase`. Both default to 30 s, which with the pause makes 65 s, so the chart sets both to 10 s: 5 + 10 + 10 = 25 s, inside 40 with a margin. Calls finish in milliseconds; the limits only matter for a stuck one.
- **A headless Service has no virtual IP** (`clusterIP: None`): its DNS name answers with every ready pod's own address instead of one address that kube-proxy spreads by connection. That matters for gRPC: the Network keeps one HTTP/2 connection for every call, and through a ClusterIP Service that one connection lands on one pod, so a second pod gets nothing and that pod's replacement breaks the calls in flight. With the headless `authorization-service`, grpc-java's `dns:///` resolver finds both pods and its `round_robin` policy opens a connection to each and sends each call to the next (our logs: 1,483 and 1,484 Charges in a 2,966-Charge run). When a pod stops, its gRPC server sends GOAWAY: the client stops sending new calls on that connection and looks the name up again.
- **Configuration comes in as environment variables.** Every address an app connects to is a Spring property, overridden by its variable (docs/architecture.md, Runtime): the chart points them at the Services (`SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/payments`). Secrets are Kubernetes Secrets, one per app holding only the variables it reads, created from `.env` by `scripts/k8s-secrets.sh` and given to the pod with `envFrom`, so the apps read the same names as in development and nothing secret is committed.
- **A Job runs pods to completion** rather than keeping them running: the load test is one (`scripts/k8s-load-test.sh`), `backoffLimit: 0` so a failed run isn't retried, and `activeDeadlineSeconds` so a call that never gets an answer, which would keep Gatling from ending, fails it instead. It runs inside the cluster because a `kubectl port-forward` from the host tunnels to one pod.
- **hostPath mounts a folder of the node into a pod.** k3d's node is a container, so `scripts/k3d-cluster.sh` mounts the repository root into it at `/b2b-payments`; the platform and the simulator mount `var/clearing` (and the simulator `var/load-test`) from there, and Keycloak and Grafana the realm and the provisioning files. The files sit where they do in development, and the atomic move that claims a Clearing File works because both pods see the same folder. It holds only on one node (M6 design, Files and secrets).
- **Tokens name the host's Keycloak.** Keycloak's hostname is `http://localhost:8180`, so every token's issuer is that, whether it was asked for from the host or from a pod through `keycloak:8180`. The resource servers check `iss` against it but fetch the signing keys from `jwk-set-uri`, inside the cluster.

## Gotchas we hit

- **Kubernetes adds variables for every Service.** Each pod gets `KAFKA_PORT=tcp://…`, `PLATFORM_SERVICE_HOST` and the like for every Service in its namespace (service links). The Kafka image turns every `KAFKA_*` variable into a broker setting, and Spring binds any variable to a property, so every pod sets `enableServiceLinks: false`.
- **The apps' images come from buildpacks,** whose defaults bit us twice: a 10 MB cap on the JVM's direct memory, and a non-root user that can't write to your folders (so the pods that write under `var/` run as you, `global.hostUser`). See [buildpacks.md](buildpacks.md).
- **k3s needs kernel modules the host must be able to load:** VXLAN for its pod network (flannel), `br_netfilter`, and netfilter matches such as `xt_comment` for kube-proxy. On a host whose kernel package was upgraded without a reboot, the running kernel's modules are gone; flannel exits with `failed to create vxlan device: operation not supported` and the k3s node restarts every few seconds. Reboot into the installed kernel.
- **`k3d image import` can report success after failing.** It logs the node's import error and then `Successfully imported`; the script checks the node's `crictl images` for each image instead.
- **grpc-java and the JDK cache DNS answers for 30 s.** grpc-java looks a name up again when a connection closes, but skips the lookup if the last was under `networkaddress.cache.ttl` (30 s by default) ago, and the JDK's resolver caches each answer as long. A rollout of 2 pods here takes seconds, so after the first old pod went, the second's going left the channel nothing but old addresses, and every Charge failed `UNAVAILABLE` for about 25 s, until the next lookup. The gRPC clients (the simulator and the load test's JVM) set `-Dnetworkaddress.cache.ttl=0 -Dsun.net.inetaddr.ttl=0`; then the rollout ended with 0 failed calls, three runs out of three.
- **A Service can't become headless in place.** `clusterIP` is immutable, so `helm upgrade` from a #114 install fails on `authorization-service`'s Service: `kubectl delete service authorization-service`, then upgrade.
- **k3d's load balancer drops a connection idle for 600 seconds.** Its nginx sits between the host's ports and the cluster with a 600 s `proxy_timeout`, so a call that answers only at the end, like seeding 25,000 cards, is cut off at about 16,600; the load-test script seeds in calls of 10,000.
- **`imagePullPolicy: Never`** for the apps' images: they exist only in the node, imported, and a pull from Docker Hub would fail. Rebuilding one doesn't restart its pod ([buildpacks.md](buildpacks.md), the `:local` tag).
