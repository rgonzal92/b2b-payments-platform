# Resilience4j

## The problem it solves here

The Network waits 1 second for each Authorization, then declines the Charge itself and sends a Reversal (ADR-0010). When `authorization-service`'s PostgreSQL is slow or down, every Authorization would sit waiting for it until that deadline: the Network sees an outage, a Reversal follows every Charge, and calls pile up holding database connections that won't come back. Resilience4j wraps the hot path's database work in a time limiter and a circuit breaker (#93), so the service answers `91` (Issuer unavailable) itself: within 500 ms while the database is slow, and at once, without touching the database, while the breaker is open. The Network gets an answer, not a timeout, and sends no Reversal.

## Mental model

- **A time limiter is a deadline on one call.** With Reactor it's `Mono.timeout` underneath: if the `Mono` hasn't produced its answer within `timeout-duration`, the limiter cancels it and signals a `TimeoutException`. Cancelling is what makes a `91` record nothing: the Authorization runs in a reactive `@Transactional` method, and Spring rolls a reactive transaction back when its subscriber cancels.
- **A circuit breaker counts outcomes and stops calling a dependency that keeps failing.** `CLOSED` lets every call through and records each as a success or failure in a sliding window (here the last 20 calls). Once at least `minimum-number-of-calls` (10) are recorded and the failure rate reaches `failure-rate-threshold` (50%), it goes `OPEN`: every call fails at once with `CallNotPermittedException`, and the database gets a rest instead of a queue. After `wait-duration-in-open-state` (5 s) the next call moves it to `HALF_OPEN`, which lets 3 trial calls through: if they succeed it closes, otherwise it opens again. No restart needed: recovery is the breaker's own trial calls.
- **The order of the operators matters.** `IssuerAuthorizationService` applies the time limiter inside the breaker (`.transformDeferred(TimeLimiterOperator.of(…)).transformDeferred(CircuitBreakerOperator.of(…))`), so a timeout reaches the breaker as a failure. The other way round, the breaker would see only errors, and a database that hangs rather than fails would never open it.
- **The fallback is a plain `onErrorResume`.** Any error past the breaker, a timeout, a refusal or a database error, becomes `91`. The Reactor module has no fallback annotation of its own, and the annotations (`@CircuitBreaker(fallbackMethod = …)`) need AOP and hide the order; the service uses neither.
- **Configuration lives in properties, instances in registries.** The Boot starter reads `resilience4j.circuitbreaker.instances.authorization-database.*` and `resilience4j.timelimiter.instances.authorization-database.*` from `application.properties` and exposes a `CircuitBreakerRegistry` and a `TimeLimiterRegistry`; the code asks each for the instance by name.
- **Metrics come with the starter.** Its Micrometer binding publishes `resilience4j.circuitbreaker.state` (a gauge per state, 1 for the current one, tagged `name=authorization-database`), the breaker's calls by outcome, and the time limiter's calls. The service's own `authorization.answers` counter counts the `91`s, registered at zero at startup like every other response code.

## Gotchas we hit

- **The Boot 4 starter isn't in the BOM.** `resilience4j-bom` 2.4.0 lists the Boot 3 starter only, so the root `pom.xml` imports the BOM for the core modules and pins `resilience4j-spring-boot4` separately, both on `resilience4j.version`. 2.4.0 is the first release with a Boot 4 starter.
- **The starter brings the core modules at runtime scope.** Its POM (and `resilience4j-reactor`'s) depends on `resilience4j-circuitbreaker` and `resilience4j-timelimiter` only at runtime, so code that names `CircuitBreakerRegistry` or `TimeLimiterRegistry` doesn't compile until the service lists both itself.
- **A timeout can't take back a commit that's already on its way.** Cancelling rolls the transaction back only if it hasn't committed. If the limit passes while PostgreSQL is confirming the commit, the Authorization is recorded although the Network got `91`. `NetworkLinkTests` reproduces it by setting `synchronous_standby_names` to a standby that never connects, which holds every commit after it is written; a resend then gets the recorded answer. The runbook covers finding and reversing these.
- **Tests that hold the database on purpose now race the limit.** Several tests order a race by holding a lock while a Charge waits; past 500 ms that Charge would answer `91`. They lift the limit while they hold the lock (`TimeLimiterRegistry.replace` with a 30-second limiter, restored afterwards), which is why the service looks the limiter up from the registry on every call instead of keeping it in a field.
- **Pause the database container, don't stop it.** `docker pause` freezes PostgreSQL with its port kept, so the service's connections hang as on a stuck server, and unpausing brings it back on the same address. A stopped container may come back on a different mapped port, which the running service would never find.
