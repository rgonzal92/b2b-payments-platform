# Resilience4j

## The problem it solves here

The Network waits a fixed deadline for each Authorization, then declines the Charge itself and sends a Reversal (ADR-0010). When `authorization-service`'s PostgreSQL is slow or down, every Authorization would wait for it until that deadline: the Network sees an outage, a Reversal follows every Charge, and calls pile up holding database connections that won't come back. Resilience4j wraps the hot path's database work in a time limiter and a circuit breaker (#93), so the service answers `91` (Issuer unavailable) itself: within the time limit while the database is slow, and at once, without touching the database, while the breaker is open. The Network gets an answer instead of a timeout, so it sends no Reversal; the service reverses the Authorization itself instead. The settings and their values are in `authorization-service`'s `application.properties`, described in [`architecture.md`](../architecture.md#the-network-link).

## Mental model

- **A time limiter is a deadline on one call.** With Reactor it's `Mono.timeout` underneath: if the `Mono` hasn't produced its answer in time, the limiter cancels it and signals a `TimeoutException`. Spring rolls a reactive transaction back when its subscriber cancels, unless its commit has already started.
- **A circuit breaker counts outcomes and stops calling a dependency that keeps failing.** `CLOSED` lets every call through and records each as a success or failure in a sliding window. Once enough calls are recorded and the failure rate reaches the threshold, it goes `OPEN`: every call fails at once with `CallNotPermittedException`, and the database gets a rest instead of a queue. After a wait the next call moves it to `HALF_OPEN`, which lets a few trial calls through: if they succeed it closes, otherwise it opens again. No restart needed: recovery is the breaker's own trial calls.
- **The order of the operators matters.** `IssuerAuthorizationService` applies the time limiter inside the breaker (`.transformDeferred(TimeLimiterOperator.of(…)).transformDeferred(CircuitBreakerOperator.of(…))`), so a timeout reaches the breaker as a failure. The other way round, the breaker would see only errors, and a database that hangs rather than fails would never open it.
- **The fallback is a plain `onErrorResume`.** Any error past the breaker, a timeout, a refusal or a database error, becomes `91`. The Reactor module has no fallback of its own, and the annotations (`@CircuitBreaker(fallbackMethod = …)`) need AOP and hide the order, so the service uses neither.
- **A `91` that reached the database is followed by the service's own Reversal.** A timeout can't tell whether the commit went through. So after a `91` that wasn't refused by the open breaker, the service calls its own Reversal path for the request ID in the background, retried with a growing pause until it succeeds or a time limit passes. M2's claim logic covers both outcomes: it reverses an approval that committed, or records the request ID as reversed (`05`) if nothing did. Either way no approval stands.
- **Configuration lives in properties, instances in registries.** The Boot starter reads `resilience4j.circuitbreaker.instances.authorization-database.*` and `resilience4j.timelimiter.instances.authorization-database.*` and exposes a `CircuitBreakerRegistry` and a `TimeLimiterRegistry`; the service takes its breaker and limiter from them once, at startup.
- **Metrics come with the starter.** Its Micrometer binding publishes `resilience4j.circuitbreaker.state` (a gauge per state, 1 for the current one, tagged `name=authorization-database`), the breaker's calls by outcome, and the time limiter's calls. The service's own `authorization.answers` counter counts the `91`s, registered at zero at startup like every other response code.

## Gotchas we hit

- **The Boot 4 starter isn't in the BOM.** `resilience4j-bom` 2.4.0 lists the Boot 3 starter only, so the root `pom.xml` imports the BOM for the core modules and pins `resilience4j-spring-boot4` separately, both on `resilience4j.version`. 2.4.0 is the first release with a Boot 4 starter.
- **The starter brings the core modules at runtime scope.** Its POM (and `resilience4j-reactor`'s) depends on `resilience4j-circuitbreaker` and `resilience4j-timelimiter` only at runtime, so code that names `CircuitBreakerRegistry` or `TimeLimiterRegistry` doesn't compile until the service lists both itself.
- **A timeout can't take back a commit that's already on its way.** Slow commits are exactly when the limit passes, so this isn't a corner case: without the self-Reversal, the Network would hear `91` while the card stays `AUTHORIZED` and the platform gets the approved Authorization. `NetworkLinkTests` reproduces it by setting `synchronous_standby_names` to a standby that never connects, which holds every commit after it is written.
- **Boot 4's R2DBC starter brings no connection pool.** Without `r2dbc-pool` on the classpath, every transaction opened its own connection and `spring.r2dbc.pool.*` settings fail at startup. The service now lists `r2dbc-pool`, and the pool's acquire time is bounded, so a call fails rather than waits for a connection a stuck database holds.
- **Tests that hold the database on purpose race the limit.** Several tests order a race by holding a lock while a Charge waits; past the limit that Charge would answer `91`. They live in `@Nested` classes with a `@TestPropertySource` that sets a long limit, which gives them their own Spring context. The enclosing class's helpers are injected from that nested context too.
- **Frozen and refused are different outages.** `docker pause` freezes PostgreSQL with its port kept, so connections hang as on a stuck server: the time limiter fires. Refusing connections (`alter database … allow_connections false` and ending its sessions) makes every call fail at once: the breaker sees errors, and the pool must reconnect once it's allowed again. The tests cover both. Stopping the container instead may bring it back on a different mapped port, which the running service would never find.
