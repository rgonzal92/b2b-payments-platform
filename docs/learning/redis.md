# Redis

## The problem it solves here

M6 runs two Gateway pods (ADR-0017), and each client's rate limit has to hold across both: a client that sends half its requests to each pod must not get twice its allowance. The pods need one shared, fast place to keep each client's count, read and updated on every request. Redis is an in-memory key-value server: a single process that runs each command, or each Lua script, one at a time, so a read-then-write needs no lock. The Gateway (#115) keeps its rate limiter's token buckets there and nothing else. The data is disposable, so Redis runs as one replica with no volume, in `compose.yaml` and in the chart (`charts/infra/templates/redis.yaml`). How the Gateway uses the buckets: [spring-cloud-gateway.md](spring-cloud-gateway.md#mental-model).

## Mental model

- **Keys, values and expiry.** Redis holds strings (and richer types we don't use) under keys, all in memory. `SETEX key seconds value` writes a value that Redis deletes by itself after that many seconds, so nothing has to clean up after a client that stops calling.
- **A token bucket is two keys.** Spring Cloud Gateway's `RedisRateLimiter` keeps, per route and key, `request_rate_limiter.{<route>.<key>}.tokens` (tokens left) and `.timestamp` (when it last counted them). The braces are a Redis Cluster hash tag that keeps both keys on one node; with one Redis they change nothing. In k3d, for example, the link's bucket is `request_rate_limiter.{remittance-link.10.42.0.1}.tokens`.
- **One Lua script does the arithmetic, atomically.** The Gateway sends `request_rate_limiter.lua` (in the Gateway jar under `META-INF/scripts/`) with the two keys and the route's rate, capacity and cost. The script reads both keys (a missing bucket counts as full), adds `rate × seconds elapsed` tokens up to the capacity, takes the request's tokens if there are enough, and writes both keys back with `SETEX` for twice the time a bucket takes to fill. It returns allowed or not, and the tokens left. Redis runs the whole script before any other command, so two pods asking at once can't both spend the last token.
- **"Now" is Redis's clock, in whole seconds.** The script reads `TIME` and keeps only the seconds, so tokens come back in steps, once a second. For the remittance link (a burst of 10, then one every 6 seconds) a `Retry-After` is 6, or 5 if a second ticked over during the burst.
- **Lettuce is the client.** Spring Boot's `spring-boot-starter-data-redis-reactive` brings Lettuce, a non-blocking Redis client on Netty, and a `ReactiveStringRedisTemplate`, which `RedisRateLimiter` runs the script through. One connection serves every request. The address is `spring.data.redis.host` and `.port`: `localhost:6379` by default, which is Compose's Redis, and `redis` in the cluster (`SPRING_DATA_REDIS_HOST`).
- **Losing Redis loses only the limit.** If Redis stops, the Gateway lets requests through and counts them (`gateway.rate.limiter.failed.open`, the `rate-limiter-redis-down` alert, [runbook](../runbooks/rate-limiter-redis-down.md)). A Redis that comes back empty treats every bucket as full: each client gets one fresh burst.

## Gotchas we hit

- **Lettuce holds commands while Redis is away.** `RedisRateLimiter` fails open only once its Redis call fails. Lettuce, though, queues commands while it reconnects until the command timeout, a minute by default, so with Redis stopped every request hung that long. `RateLimits.failFastWhileRedisIsDown` sets Lettuce's `DisconnectedBehavior.REJECT_COMMANDS` through Boot's `LettuceClientOptionsBuilderCustomizer`. `spring.data.redis.timeout=250ms` and `connect-timeout=250ms` cover a Redis that is connected but answers nothing. `GatewayTests.WithRedisStopped` fails without the customizer.
- **Lettuce comes back by itself, after a while.** Its `ConnectionWatchdog` reconnects with a backoff of up to about 30 seconds, so limits return within that time of Redis being ready. On k3d it took 14 seconds. No Gateway restart is needed.
- **Stopping a Redis in a test that others share breaks them.** The test that stops Redis starts its own container in a nested context, and each test begins by flushing the shared one (`FLUSHALL`) so it starts with full buckets.
- **The limiter's error log floods.** `RedisRateLimiter` logs an `ERROR` with a stack trace for every request it lets through unlimited. That logger is turned off. The counter, its alert and the Gateway's `/actuator/health` (`DOWN` while Redis is) carry the signal instead.
