# Kafka

## The problem it solves here

M5 moves Authorization into its own service (ADR-0016). The service must answer Charges on the platform's cards while the platform is down, so it needs its own copy of them, and the platform must tell another process about every issued, cancelled or expired card reliably. Spring Modulith's in-process events stop at the JVM (ADR-0008); Kafka is the durable log between the two processes. The platform keeps using the event publication registry as its outbox and Spring Modulith externalizes the events from it, so a crash between the database commit and the send leaves the event recorded, not lost.

## Mental model

- **A broker stores named, append-only logs: topics.** A topic is split into partitions; each message goes to one partition by its key, and Kafka guarantees order only within a partition. The `cards` topic has 3 partitions, keyed by Card Token, so one card's events stay in the order they reached the topic and three consumers can share the work. That is not the order the platform published them in: see the gotcha on ordering below.
- **A message is a key, a value and headers.** Card events carry the Card Token as key, the event as JSON, and `event-type` with `CardIssued`, `CardCancelled`, `CardExpired` or `CardCleared`. Jackson 3 serializes the records; Spring Modulith's Kafka module sets `ByteArraySerializer` and a Jackson `RecordMessageConverter`.
- **Publishing is the registry's job.** An event annotated `@Externalized("cards::#{cardToken}")` — topic `cards`, key from the event's `cardToken` — gets a row in `modulith.event_publication` in the same transaction as the change (ADR-0008). After the commit an `@ApplicationModuleListener` sends it; the row's `completion_date` is set when `KafkaTemplate.send` completes. A failed send or a stopped platform leaves the row incomplete, and `spring.modulith.events.republish-outstanding-events-on-restart=true` resends them at the next start.
- **Delivery is at least once.** Kafka itself can redeliver, and the registry resends incomplete publications, so every consumer keys its write on the event's natural ID (the Card Token and event type) and does nothing on the second delivery. `authorization-service` consumes `cards` (see below).
- **The broker is dumb in the useful way.** Topics, partitions and offsets live in Kafka; the producer knows only the topic and key. Consumers track their group's committed offset, so a stopped consumer resumes where it left off (the design's 7-day retention bounds how far back a new one can start).
- **Local Kafka is one KRaft broker, not ZooKeeper.** `compose.yaml` starts `apache/kafka:4.2.1` with the same listener setup Testcontainers' `KafkaContainer` uses; tests start their own container through `TestKafka`. Kafka is plaintext and unauthenticated on localhost; M7 adds mutual TLS.

## The consumer's side (#88)

- **A consumer group shares a topic's partitions and owns its offsets.** `authorization-service` reads `cards` as the group `authorization-service`: each partition goes to one consumer in the group, which reads its messages in order, and the group's committed offset says where it resumes after a restart. Another group reading the same topic gets every message again, independently.
- **Commit after the write, never before.** Spring Kafka commits a batch's offsets only once the listener has returned for each of its records, and `CardsTopicListener` returns only once the card copy is written. A crash in between redelivers the message, which is why every write does nothing the second time; committing first would lose the event instead.
- **`auto-offset-reset=earliest` decides where a new group starts.** With no committed offset (a new service, or a renamed group) the consumer starts at the oldest message the topic still holds, within the 7-day retention, rather than only at new ones, so it sees every card issued before it started. A group that has committed resumes from its offset whatever this says.
- **A failure blocks the partition, on purpose.** Spring Kafka's default error handler tries a failing record ten times at once, then logs and skips it, which would lose a card for good when the database is briefly down. `CardsTopicErrorHandling` retries instead with a growing pause (1 s doubling to 30 s) and no limit, so the partition waits and resumes where it stopped once the database is back; other partitions carry on. Only a message that can never succeed is skipped and logged by partition and offset, never its contents: one with no `event-type` header or one the service doesn't use, and one whose JSON is malformed or lacks a field the service needs (Jackson's error).

## The platform's consumer (#91)

- **One consumer group per module, not per app.** Within one group Kafka hands each partition to one listener, so two `@KafkaListener`s in the platform sharing a group would each see only some cards' events. `payables` reads `authorizations` in its own group, `platform-payables`, and takes only `CardOnFile`; `authorization`'s listener for the Authorization events (#92) gets a group of its own. Each module then owns its offsets and its failures, and reads every message, ignoring the types it doesn't use.
- **The same retry-forever, skip-the-unreadable error handling** as the service (`KafkaConsumerConfiguration`). Spring Boot applies the one `DefaultErrorHandler` bean to every listener in the app.

## The service's outbox (#90)

`authorization-service` publishes on the `authorizations` topic through an outbox of its own, not Spring Modulith's registry: it isn't a Modulith app, and it reaches its database through R2DBC.

- **The transactional outbox pattern.** Writing to the database and sending to Kafka are two systems with no shared transaction: send after the commit and a crash in between loses the event; send before and a rollback publishes something that never happened. Instead the change and its event are inserted in one database transaction, into the `outbox` table, and a separate relay sends the committed rows later. The event is then exactly as durable as the change it reports.
- **The relay is a polling publisher.** `OutboxRelay` wakes 100 ms after its last pass, reads unsent rows in id order, sends each, and sets its `sent_at` once Kafka acknowledged it. It runs on the scheduler's thread, never the hot path, which only pays for one more insert in a commit it was making anyway.
- **Order comes from an identity column, and from locks.** Rows are read `order by id`, never by timestamp, whose clock can tie or step back. An id is taken when the row is inserted, not when it commits, so two transactions can commit in the other order; the relay doesn't care, since it reads every unsent row each pass rather than resuming after the highest id it sent. What matters is one card's order, and each event is written after its change took the card's row lock, so one card's ids follow its commits.
- **One relay at a time, or order is lost.** A pass is one transaction that starts with `pg_try_advisory_xact_lock`: a second pass, from a slow scheduler or another instance, gets `false` and does nothing, and the lock ends with the transaction, so a crashed relay can't hold it. `FOR UPDATE SKIP LOCKED` would let two relays send different rows at once and a card's events cross. Sends go one at a time, each acknowledged before the next, and the first failure ends the pass, so a later event never lands ahead of an earlier one that failed.
- **One pass, one transaction, through the proxy.** `@Transactional` works only on a call through the bean's proxy: a scheduled method calling `this.relay()` in the same class ran each statement in its own transaction, so the advisory lock was released as soon as its `select` ended. `OutboxRelaySchedule` is a separate bean that calls `OutboxRelay`, and a test checks that the lock is still held while the scheduled pass sends.
- **At least once, again.** Each pass's `sent_at` updates commit together at its end, so a crash in the middle of a pass sends again, unchanged, every row that pass had already sent. So the platform's consumer keys its write on the event's natural ID: the request ID and event type for the two Authorization events, which share a request ID, and the Card Token for `CardOnFile`.

## Gotchas we hit

- **An event published outside a transaction is silently dropped.** `@ApplicationModuleListener` is a `@TransactionalEventListener`; with no transaction running, it never fires and the registry never records a row. `SingleUseCards.cancel` publishes `CardCancelled`, and it needed `@Transactional` so the status change and its event commit together — the saga's compensation already runs inside one, but a direct call (as tests make) did not.
- **Externalization adds no event-type header by default.** `@Externalized` names the topic and key only. `KafkaExternalizationConfiguration` adds `event-type` from the event's simple class name and sets `serializeExternalization(true)`, so only one send runs at a time.
- **Serialized is not ordered.** Spring Modulith sends each event from its own thread after its transaction commits, and `serializeExternalization` only stops two sends running at once; whichever thread gets there first goes first. Two events for one card committed back to back (issued, then cancelled) can reach the topic in either order: a probe issuing and cancelling 100 cards saw it once, and CI once saw `CardExpired` before `CardIssued`. Restarting resends incomplete publications the same way. So Kafka's per-key order holds only from the topic on, and every consumer must be order-tolerant: `authorization-service` applies card events so that any order gives the same result.
- **A topic isn't created with your partitions unless you say so.** Kafka's auto-create uses one partition. A `NewTopic` bean declares `cards` with 3 partitions and replication factor 1; Spring Boot's `KafkaAdmin` applies it at startup. Publishing still works while the broker is down — the sends fail, and the publications wait in the registry.
- **The event is the contract, so it carries hashes, never secrets.** `CardIssued` has the PAN's and security code's keyed hashes from `vault` (base64-encoded HMAC-SHA-256 under `vault.hash-key`), expiry, amount, currency and the Supplier's Acceptor ID; no PAN or security code appears in a message, a log or the publication table. The Acceptor ID travels into `Cards.issueSingleUse` from the saga because `cards` can't call `suppliers` (Spring Modulith forbids the cycle).
- **Tests should not talk to Kafka by accident.** Every test context with `spring-modulith-events-kafka` on the classpath would otherwise try `localhost:9092`. Test properties set `spring.modulith.events.externalization.enabled=false`; `CardEventsTests` imports a Kafka container and turns it back on.
- **A consumer can create the topic it subscribes to, with one partition.** The broker auto-creates a missing topic when a consumer asks for it, with one partition. When the owner later declares three, its `KafkaAdmin` adds the other two, but a consumer already subscribed keeps reading only the first until its metadata refreshes, up to five minutes later (`metadata.max.age.ms`). The e2e test caught the service missing the platform's first `CardIssued` this way. The platform declares `authorizations` too, so whichever app starts first creates it with its three partitions before any listener subscribes. The service likewise declares `cards` (#91), so either app may start first.
- **A failed send waits for someone to ask again.** Spring Modulith marks a publication `FAILED` when Kafka refuses it, and by default sends it again only at the next start. `EventResubmissionSchedule` calls `IncompleteEventPublications.resubmitIncompletePublicationsOlderThan` every minute, for publications over a minute old, so a short outage heals itself; `CardEventsTests` pauses the broker's container while a card is issued to prove it. The resend can duplicate an event or put it after the card's later ones, which consumers already tolerate.
- **A message with no value or no `event-type` header can't be read either.** `JSON.readValue(null)` throws an `IllegalArgumentException`, not a Jackson error, so the error handler would retry it forever and block its partition. The listener checks both first and skips the message with a log line.
- **Spring Modulith's Kafka support changes the consumer's defaults.** Its `kafka-json.properties` sets `spring.kafka.consumer.value-deserializer` to `ByteArrayDeserializer`, so a `ConsumerRecord<String, String>` listener fails with a `ClassCastException`. The platform sets the value deserializer back to `StringDeserializer`.
- **Even `partitionsFor` needs deserializers.** A `KafkaConsumer` built only with `bootstrap.servers` fails with `Invalid value null for configuration key.deserializer`.
- **Kafka 4's producer lingers 5 ms by default.** `linger.ms` waits for more messages to batch with each send; a relay that waits for each acknowledgement before the next send never has one, so it would pay 5 ms a message. The service sets `spring.kafka.producer.properties.linger.ms=0`.
- **Don't send from R2DBC's event loop.** `KafkaTemplate.send` can block for up to `max.block.ms` (60 s) while it waits for the broker's metadata. Inside a reactive pipeline it would run on whichever thread delivered the last row, an R2DBC event-loop thread the hot path shares, so the relay subscribes to each send on Reactor's `boundedElastic` scheduler.
