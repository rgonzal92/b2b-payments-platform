# Spring Cloud Gateway

## The problem it solves here

M6 runs two copies of every app and puts one address in front of the platform's REST API (ADR-0017). Something has to take every request first: send it to a platform pod, and refuse what the platform should never have to look at, so a flood of requests without a token stops at the edge instead of reaching the platform's threads and database. M6 also limits each client's rate there, through Redis (#115). Spring Cloud Gateway is Spring's reverse proxy: a Spring Boot app whose routes forward requests to other services, with Spring Security in front of them. The `gateway` module (#113) routes `/v1` to the platform, checks the Keycloak token and limits each client's rate (#115); the platform stays the authority on roles and Buyers.

## Mental model

- **A route is a predicate, a list of filters and a destination.** `application.properties` declares two routes to `gateway.platform-uri` (`http://localhost:8080` in development, the platform's Service in the cluster through `GATEWAY_PLATFORM_URI`): `remittance-link` (`GET /v1/remittance-links/*`) and, after it, `platform` (`Path=/v1/**`, every other API path). The first route whose predicates match wins, so the order matters. A request that matches no route gets `404` from the Gateway itself.
- **Rate limiting is a token bucket per key, kept in Redis.** Each key has a bucket holding up to `burstCapacity` tokens that refills at `replenishRate` tokens a second; a request takes `requestedTokens` (1 by default) or is refused. The stock `RequestRateLimiter` filter asks a `KeyResolver` bean whose bucket a request draws on, then `RedisRateLimiter` runs one Lua script in Redis that refills the bucket for the time elapsed and takes the tokens atomically, so every Gateway pod shares the same buckets. The `platform` route keys on the token's `azp`, the Keycloak client (`RateLimits.keycloakClient`): bursts to 40, then 20 a second. The remittance link has no token, so its route keys on the connection's address (`RateLimits.clientIp`): 10 a minute. Redis stores two short-lived keys per bucket (`request_rate_limiter.{route.key}.tokens` and `.timestamp`), so its state is disposable.
- **Over the limit: `429` Problem Details with `Retry-After`.** The filter adds `X-RateLimit-Remaining`, `-Replenish-Rate`, `-Burst-Capacity` and `-Requested-Tokens` to every response. With `throwOnLimit=true` it raises an exception instead of completing an empty `429`, and `GatewayProblems` turns that into Problem Details with `Retry-After`: the tokens short over the refill rate, rounded up to whole seconds (1 for a client, up to 6 for the link).
- **The limiter fails open.** `RedisRateLimiter` itself catches any Redis error, logs it and allows the request, reporting `-1` tokens remaining. `RateLimits.FailOpenCountingRateLimiter` counts those as `gateway.rate.limiter.failed.open`, which Grafana alerts on (ADR-0017, [runbook](../runbooks/rate-limiter-redis-down.md)).
- **The request goes on almost as it came.** Path, query, body and `Authorization` reach the platform unchanged. The headers don't all: the Gateway drops the hop-by-hop headers HTTP says a proxy must, and `X-Application-Context`; it sends the platform's own address as `Host`, not the one the client used; and with no trusted proxies configured it drops every `Forwarded` and `X-Forwarded-*` header the client sent and adds none (see the gotchas). The platform checks the same token again, so the Gateway adds a layer and takes nothing away: `GatewayTests` shows a token without a platform role passing the Gateway and getting the platform's `403`.
- **The Gateway's own errors are Problem Details too.** A path no route serves gets `404`, a platform that refuses the connection `502` ("The platform can't be reached."), and any other error the Gateway raises its own status (a `504` once `httpclient.response-timeout` is set, untested so far), each as `application/problem+json` from `GatewayProblems`, an `ErrorWebExceptionHandler` ordered before Spring Boot's, which would answer its own JSON. The platform's errors pass through as the platform wrote them.
- **It runs on WebFlux and Netty.** Gateway Server WebFlux, the original flavour, proxies on Reactor Netty without a thread per request; Gateway Server Web MVC is the servlet flavour. So the Gateway's security is Spring Security's reactive one: a `SecurityWebFilterChain` built from `ServerHttpSecurity`, as `authorization-service`'s HTTP chain is ([reactor-webflux.md](reactor-webflux.md)).
- **Security runs before routing.** Spring Security's web filters run before the Gateway's handler picks a route, so a refused request never opens a connection to the platform. `SecurityConfig` makes the Gateway an OAuth2 resource server on the same `issuer-uri` as the platform: every path needs a valid token (signature, expiry, issuer) except the Gateway's own `/actuator/health/**` and `GET /v1/remittance-links/*`, whose link token is the Supplier's credential and which the platform checks.
- **A release train, not a version.** Spring Cloud ships its projects (Gateway, Commons, ...) together as a release train with one BOM, `spring-cloud-dependencies`, and each train supports specific Spring Boot generations. The root `pom.xml` imports train 2025.1.3 (Oakwood), which supports Boot 4.0.x and, from 2025.1.2, 4.1.x; it brings Gateway 5.0.3. The 2026.0.x train is for Boot 4.2. Spring Initializr's `start.spring.io/actuator/info` lists the same ranges under `bom-ranges`.

## Gotchas we hit

- **The bearer entry point completes the response empty.** The platform's servlet entry point writes its Problem Details body after `BearerTokenAuthenticationEntryPoint` has set the status and `WWW-Authenticate`. The reactive `BearerTokenServerAuthenticationEntryPoint` ends with `response.setComplete()`, which commits the response, so writing a body after it fails with `UnsupportedOperationException` and the client gets an empty `401`. The Gateway hands it a response decorator whose `setComplete()` writes the body instead, so the headers stay the bearer entry point's.
- **The platform never learns the client's address.** Gateway 5.0 trusts no proxy unless `spring.cloud.gateway.server.webflux.trusted-proxies` is set (a regular expression of addresses), and until then it strips every `Forwarded` and `X-Forwarded-*` header, the client's included, and adds none of its own. That stops a client forging `X-Forwarded-For`, but the platform then sees every request as coming from the Gateway. So the remittance link's per-IP limit keys on the connection's remote address, never on a header any client can send; `GatewayTests` shows a forged `X-Forwarded-For` getting no fresh allowance. In the k3d cluster that address is not the client's: k3d's load balancer and k3s's ServiceLB forward every host connection, and the Gateway sees `10.42.0.1`, the node's pod-network gateway, so every client on the host shares one link bucket. Fine for one machine; a real deployment would trust its load balancer explicitly (`trusted-proxies`) and take the address it forwards.
- **Boot's error handler doesn't speak RFC 9457.** Without `GatewayProblems`, an unmatched path or an unreachable platform answers Spring Boot's own JSON (`timestamp`, `path`, `error`), and an unreachable platform is a `500`, not a `502`. Problem detail settings for WebFlux (`spring.webflux.problemdetails.enabled`) cover only controller exceptions, and the Gateway has no controllers. Spring's `ProblemDetail` also leaves out `type` when it is `about:blank`, which RFC 9457 says is what a missing `type` means.
- **The properties moved.** Gateway 4.3 put the WebFlux server's settings under `spring.cloud.gateway.server.webflux.*`; 5.0's configuration metadata lists only that prefix, while many guides still show `spring.cloud.gateway.routes`.
- **Spring Security closes everything by default.** Adding the resource server starter makes even `/actuator/health` answer `401`, which a Kubernetes probe would read as a dead pod; the chain opens health explicitly, as `authorization-service`'s does.
- **Import the train's BOM after Resilience4j's.** In Maven the first import of a managed dependency wins, and the Spring Cloud BOM also pins Resilience4j modules (through Spring Cloud Circuit Breaker). The root POM imports it last, so `resilience4j-bom` 2.4.0 keeps its pins for `authorization-service`.
- **Lettuce holds commands while Redis is away.** `RedisRateLimiter` fails open only once its Redis call fails, and Lettuce, Spring Boot's Redis client, queues commands while it reconnects until the command timeout, a minute by default. With Redis stopped, every request then hung for that long. `RateLimits.failFastWhileRedisIsDown` sets Lettuce's `DisconnectedBehavior.REJECT_COMMANDS` through Boot's `LettuceClientOptionsBuilderCustomizer`, and `spring.data.redis.timeout=250ms` covers a Redis that is connected but answers nothing. Lettuce reconnects with a backoff of up to 30 seconds, so limits come back a few seconds after Redis does.
- **The stock limiter's `429` is empty.** On a refusal `RequestRateLimiter` sets the status and completes the response, with no body and no `Retry-After`. Its `throwOnLimit` argument raises `HttpClientErrorException.TooManyRequests` instead, which reaches the `ErrorWebExceptionHandler` with the `X-RateLimit-*` headers already on the response.
- **The bucket's rate is whole tokens a second.** `replenishRate` is an integer per second, so 10 a minute is a bucket of 60 tokens refilling at 1 a second, with each request costing 6 (`requestedTokens`).
- **A route without a key is refused with `403`.** If the `KeyResolver` returns nothing, as `keycloakClient` does for a request without a token, the filter answers `403` (`denyEmptyKey`, on by default). That broke the remittance link until it got its own route keyed by address.
- **Two `KeyResolver` beans need a default.** The filter factory takes one `KeyResolver` as its default, so with two the context fails to start; `keycloakClient` is `@Primary`, and the link's route names its own with `key-resolver=#{@clientIp}`.
