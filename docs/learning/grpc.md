# gRPC and protobuf

## The problem it solves here

Every Charge on a card makes the Network ask the Issuer (`authorization-service` since the cutover, #92; the platform before), in real time, whether to approve it; 99% of answers must leave within 100 ms, and the Network gives up after 1 second (ADR-0010). Real Networks send these requests as ISO 8583 binary messages over long-lived TCP connections. gRPC gives the same shape, a typed request and answer over a connection that stays open, without writing a binary codec first (ADR-0006). The contract is a `.proto` file both sides generate code from, so the platform and the simulator's Network can't drift apart, and its field names are ISO 8583's, so a later move to real ISO 8583 is a mapping.

## Mental model

- **Contract first.** `contracts/src/main/proto/issuer_authorization.proto` defines the `IssuerAuthorization` service (`Authorize`, `Reverse`) and its messages. At build time `protoc` generates a Java class per message (with a builder) and `IssuerAuthorizationGrpc`, which holds the client stubs and the `IssuerAuthorizationImplBase` the platform extends. Generated code is never edited: change the `.proto` and rebuild.
- **Field numbers are the wire format, names are for people.** Protobuf encodes each field as its number and a compact binary value, never its name. Renaming a field is safe; changing or reusing a number breaks every client already deployed. Adding a field with a new number is backward compatible: old readers skip it.
- **proto3 has no null.** An unset string reads as `""` and an unset `int64` as `0`. A decline's authorization code is therefore `""` on the wire, and `authorization-service` stores it as `NULL`.
- **One HTTP/2 connection, many calls.** A gRPC call is an HTTP/2 request: `POST /payments.network.v1.IssuerAuthorization/Authorize` with the protobuf bytes as its body. HTTP/2 multiplexes many calls over one connection, so after the first call there's no TCP or TLS handshake on the latency budget.
- **Deadlines travel with the call.** A client sets a deadline (`withDeadlineAfter`), sent as the `grpc-timeout` header; when it passes, the client gets `DEADLINE_EXCEEDED` and the server's call is cancelled. Cancelling the call doesn't undo work the server has started: the platform's Authorization runs on in its transaction and may still approve, and the client can't tell whether it did. The Network waits 1 second, then declines the Charge and sends a Reversal ([below](#the-client-side-the-simulators-network)). The platform's tests use 5 seconds, so a hang fails fast instead of stalling the build.
- **A gRPC status says whether the call worked; an ISO 8583 response code says what the Issuer answered.** A decline is a successful call: status `OK`, `response_code` `"14"` (invalid card), `"54"` and the rest ([`authorization-message.md`](authorization-message.md)). gRPC statuses are for calls that never got an answer: `UNAUTHENTICATED` (no or bad token), `PERMISSION_DENIED` (not the Network), `INVALID_ARGUMENT` (no retrieval reference number to answer under or to reverse), `UNIMPLEMENTED` (a method the service doesn't override), `DEADLINE_EXCEEDED`, `UNKNOWN` (a bug). Mixing the two would make the Network treat a bug as a decline, or a decline as an outage.
- **Metadata carries the token.** Metadata is gRPC's name for HTTP/2 headers. The Network sends `authorization: Bearer <token>`, a Keycloak token for the `network` client. Spring gRPC's `GrpcSecurity` builds an `AuthenticationProcessInterceptor`, a server interceptor that runs before the service: it validates the token with the same JWT decoder, issuer and `roles` claim as REST and requires `ROLE_network` for every call (`SecurityConfig`).

## How it's built here

The platform served the Network link as drawn here from M2 until the cutover (#92). Since then `authorization-service` serves it on the same `127.0.0.1:9090`, with the same rules and security, from its own copy of the cards and with a reactive hot path ([architecture](../architecture.md#authorization-service)); the platform runs no gRPC server.

```text
Network ──HTTP/2, authorization: Bearer <network token>──▶ Netty on 127.0.0.1:9090
  └─ AuthenticationProcessInterceptor     no or bad token: UNAUTHENTICATED; no ROLE_network: PERMISSION_DENIED
       └─ IssuerAuthorizationService       @GrpcService, extends IssuerAuthorizationImplBase
            ├─ Authorizations.authorize    one transaction: the Authorization rules, then the answer
            │    ├─ vault.cardFor(PAN)      Card Token through the PAN's keyed hash; none: 14
            │    ├─ vault.securityCodeMatches, cards.find, AuthorizationRules.decide
            │    ├─ insert into "authorization".authorizations … on conflict do nothing
            │    └─ approved: cards.authorize(token)   ACTIVE → AUTHORIZED in one conditional update
            └─ Authorizations.reverse      one transaction, acknowledged 00: claim the request ID as
                                           reversed, or reverse its approved Authorization
```

- **Spring Boot's own gRPC support.** `spring-boot-starter-grpc-server` runs a Netty gRPC server beside Tomcat and exposes every `BindableService` bean (`@GrpcService`). Boot's parent configures `io.github.ascopes:protobuf-maven-plugin` with matching `protoc` and `protoc-gen-grpc-java` versions, so `contracts` only declares the plugin. Older guides use other libraries (`net.devh`, LogNet); this project doesn't.
- **Plaintext, on this machine only.** The server listens on `127.0.0.1` (`spring.grpc.server.address`; the default is every interface), and the connection isn't encrypted: mutual TLS arrives in M7.
- **Tests talk to a real server.** Each test context's server takes a free port (`spring.grpc.server.port=0`), read with `@LocalGrpcServerPort`; the test opens a plaintext Netty channel and sends the token with Spring gRPC's `BearerTokenAuthenticationInterceptor`. `authorization-service`'s `NetworkLinkTests` does so with a stand-in token decoder, the token checks included (`aCallWithoutTheNetworksTokenIsRefused`). Until the cutover the platform's `NetworkAuthenticationTests` (real Keycloak tokens) and `AuthorizeTests` did.

## The client side: the simulator's Network

```text
GlobexSupplier.charge(invoice)         the card it read through its link
  └─ GlobexAcquirer.charge(card)       builds the AuthorizationRequest: PAN, amount, YYMM expiry, STAN, request ID, Acceptor ID, …
       └─ Network.authorize(request)   IssuerAuthorizationBlockingStub, withDeadlineAfter(1 s) per call
            │    DEADLINE_EXCEEDED or UNAVAILABLE: answers 91 itself at once, and sends Reverse(request ID)
            │    in the background, each attempt with its own deadline, four attempts at most
            └─ channel "platform"      static://localhost:9090, plaintext
                 ├─ grpc.client observation                 Boot's global interceptor
                 └─ BearerTokenAuthenticationInterceptor    authorization: Bearer <network token>, on every call
```

- **A channel is a long-lived link to one server, and a stub is a typed handle on it.** A `ManagedChannel` opens its HTTP/2 connection on the first call, reconnects on its own, and carries every call after that, so one channel serves the whole app; a channel per call would pay for a new connection every time. A stub (`IssuerAuthorizationGrpc.newBlockingStub(channel)`) is cheap: it turns a method call into a gRPC call on the channel. The blocking stub waits for the answer on the caller's thread, which suits the demo.
- **Spring Boot builds named channels from configuration.** `spring-boot-starter-grpc-client` provides a `GrpcChannelFactory`; `createChannel("platform", options)` reads `spring.grpc.client.channel.platform.*`. Its `target` is `static://` plus `simulator.platform-grpc-address` (`localhost:9090` by default; the tests point it at their own servers). In the k3d cluster the chart sets the target to `dns:///authorization-service:9090` and `default.load-balancing-policy` to `round_robin`, which spreads the calls over the service's pods ([`kubernetes.md`](kubernetes.md)). Without `ssl.enabled` or an `ssl.bundle` the channel is plaintext, like the server's until M7. The factory shuts its channels down when the app stops.
- **A client interceptor sees every call before it leaves.** It can add metadata, time the call or refuse it. `BearerTokenAuthenticationInterceptor` asks its token supplier for a token at the start of each call and sends it as `authorization: Bearer <token>`. Interceptors for one channel go in `ChannelBuilderOptions.withInterceptors`. Boot adds its global ones, such as the `grpc.client` observation, to every channel as well.
- **The token comes from the same place as REST's.** The supplier asks the simulator's `OAuth2AuthorizedClientManager` for the `network` registration's token (client credentials, `NETWORK_CLIENT_SECRET`). The first call fetches it from Keycloak, and later calls reuse it until it is close to expiring.
- **Every call gets its own deadline.** A stub is immutable: `issuer.withDeadlineAfter(deadline)` returns a new stub whose next call must finish by then, so the Network makes one per call. A deadline set once on the shared stub would be a single moment, long past by the second Charge. The deadline is the setting `simulator.network.authorization-deadline` (`1s`; the slow-platform test uses `200ms`).
- **Decline, then reverse.** When `Authorize` ends `DEADLINE_EXCEEDED` (the platform is slow) or `UNAVAILABLE` (it can't be reached, or the connection dropped mid-call), the Network doesn't know whether the platform approved. It owes Globex an answer now, so it answers with a decline it makes up itself, `91` (issuer unavailable, no authorization code), and sends `Reverse` for the same retrieval reference number, under a STAN of its own and the time it sends it. The Reversal goes out in the background, on Boot's application task executor, so Globex isn't kept waiting while it is sent or retried. If the platform approved the Authorization too late, the Reversal cancels it; if the platform never saw the request, the Reversal leaves a placeholder, and the late Authorization answers `05` (`authorization-message.md`). Any other status, such as `UNAUTHENTICATED`, is a fault rather than an answer, and fails the Charge as before.
- **The Reversal is retried, the Authorization isn't.** A Reversal is safe to repeat: the platform reverses an Authorization once and acknowledges every Reversal with `00`. So the Network resends the same Reversal through Spring's `RetryTemplate`, up to four attempts, 100, 200 and 400 ms apart, each with its own deadline. When all four fail, it logs the retrieval reference number at `ERROR` for someone to follow up ([runbook](../runbooks/network-cant-reach-platform.md)); Globex has had its decline all along. Resending the Authorization instead would leave Globex waiting past the deadline it was promised.
- **The simulator's tests use a stub server.** `StubIssuer` runs a real Netty gRPC server on a free loopback port, with a stub `IssuerAuthorizationImplBase` and a server interceptor that records each call's `authorization` metadata beside its request or Reversal. It can answer `Authorize` late (`answerAfter`) to play a slow platform. The test points `simulator.platform-grpc-address` at it, or at a free port nothing listens on to play an unreachable one.

## Gotchas we hit

- **Boot already secures gRPC, but only half way.** With a `JwtDecoder` in the context, Boot auto-configures an interceptor that requires *any* valid token: the "no token" test passed before we wrote any security code, while `acme-erp`'s token got answers. Our own `AuthenticationProcessInterceptor` bean replaces Boot's (it backs off when one exists) and requires `ROLE_network`.
- **A forged token fails before any rule.** Authentication runs first, so even `permitAll()` answers `UNAUTHENTICATED` to a token the realm didn't sign; only a missing token reaches the rules as anonymous.
- **`roles` → `ROLE_network` comes for free.** `GrpcSecurity`'s `jwt()` reuses the `JwtAuthenticationConverter` bean Boot builds from `authorities-claim-name=roles`, so gRPC and REST read roles the same way.
- **The starter adds reflection and health services** (`grpc-services`). The rule covers them too: every call needs the Network's token.
- **Fixed ports and tests don't mix.** Every cached Spring test context starts its own gRPC server, and other builds may run on the same machine; on 9090 they would collide. The test configuration sets port `0`; the end-to-end test, which starts `authorization-service` with only its main properties, picks a free port for it.
- **A protobuf message's `toString` prints every field**, PAN and security code included. Nothing logs a request; a throwaway change logging one made `CorePathTests` fail on the PAN in the captured logs.
- **`authorization` is a reserved word in PostgreSQL.** `select … from authorization.authorizations` is a syntax error; SQL must say `"authorization".authorizations`. Flyway quotes schema names itself, and the PAN search builds names with `format('%I.%I')`, which quotes them too. The table is plural so it needn't be quoted as well.
- **A method you don't override answers `UNIMPLEMENTED`.** The generated `ImplBase` did that for `Reverse` until #33 overrode it.
- **An exception in a service becomes `UNKNOWN`, without its message.** The client never sees the exception's text, and Spring gRPC logs it only at `DEBUG`. Good for keeping PANs out of answers, harder for debugging.
- **Traces record the call, not its content.** Micrometer's gRPC observation names the span after the full method name and records the status and the caller's address and port; never message fields or metadata.
- **Spring gRPC's `ClientCredentialsTokenSupplier` asks Keycloak for a new token on every call.** It builds a token client from the client registration and keeps nothing, so every Charge would wait on Keycloak inside its latency budget. The Network's supplier goes through the authorized-client manager instead, which keeps the token until it expires.
- **A bare lambda won't compile as the interceptor's token supplier.** `BearerTokenAuthenticationInterceptor` has constructors for both `Supplier<String>` and Spring gRPC's `TokenSupplier`, and a lambda fits both, so `javac` reports the call as ambiguous. Declare the lambda as a `TokenSupplier` first.
- **A deadline counts from when it's set, not from when the request leaves.** The Network's first call opens the channel's connection and fetches the `network` token from Keycloak inside the interceptor, all before any byte reaches the platform, and all of it counts against the deadline. With a 200 ms deadline in a cold test JVM, the first Charge timed out before the stub saw it, so the slow-platform test makes one Charge before it starts; and against a closed port the same short deadline ended the call `DEADLINE_EXCEEDED` rather than `UNAVAILABLE`, so the unreachable-platform test keeps the default. In the end-to-end test the first Charge took about 190 ms of its 1 second, sign-in and connection included.
- **The simulator starts no gRPC server, even with the server starter on its classpath.** In the end-to-end test both apps share one classpath, so the simulator sees `spring-boot-starter-grpc-server` too. Boot starts a server only for an app with a `BindableService` bean, and the simulator has none.
